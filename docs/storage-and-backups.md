# Storage nodes, external storage and database backups

Storage nodes use the existing Docker daemon with `docker.mode: storage`. They can provision managed PostgreSQL, key-value stores, ClickHouse and SeaweedFS object storage, and execute native backup jobs. Generic application containers and builds remain on Docker and Build nodes. Existing `databases` nodes retain their configuration and database data; upgrading a daemon does not move its data directory.

Enroll a new **Storage** node through the node enrollment dialog or `scripts/setup-storage-node.sh`. The existing `docker.database.storage_root` remains the allocation root for compatibility. Managed databases, object storage and backup workspaces use ext4 images on that disk and respect the configured free-space reserve. An image is promised its full size even while it occupies less, so a create or a disk grow is accepted only when every image on the node can still reach its size next to the reserve; a node whose images are promised more than its disk holds (from an older release) shows a warning on its instances and refuses further creates and grows until space is freed. Every hour, and right after managed storage compacts deleted objects, the instances' filesystems discard their free blocks, so the space of deleted data goes back to the node. If an instance's filesystem still goes read-only (the node's disk filled up or failed), the node stops its engine, checks and repairs the disk with `e2fsck -p`, mounts it again and starts the engine; the instance shows the repair while it runs and its outcome afterwards. A disk `e2fsck -p` cannot repair leaves the instance in error with the reason; restarting it tries the repair again. Gateway also removes, every 30 minutes, what a managed instance it no longer has left on its node: a container left by a delete or an interrupted recreation, or a record zeroed by a crash with its image and mount point; an id is removed only when Gateway has no database or storage of it in two checks at least 5 minutes apart, the node refuses the removal of an id it has a readable record of, and each removal is in the audit log (`node.managed_leftover.removed`). An engine that stops on its own (a crash, an out-of-memory kill) is started again, and the instance shows how often that happened in the last 24 hours; one that keeps stopping is shown stopped, not ready. Set CPU, memory and disk limits when provisioning a resource. A resize the node refuses (too little disk) changes nothing: the instance stays ready with its links and shows why.

## Storage connections

The Storage section connects to AWS S3, Cloudflare R2, MinIO and compatible S3 endpoints, FTP, explicit or implicit FTPS, and SFTP. File protocols expose directories below the configured base path as buckets. SFTP requires the server's SHA256 host-key fingerprint; FTPS verifies the server certificate using the system trust store or a configured private CA.

## Managed object storage

New managed storage clusters run SeaweedFS 4.47 (catalog `seaweedfs-4.47`), pinned to an immutable image digest. Storage nodes pull it from the Gateway mirror `ghcr.io/the-square-labs/gateway/seaweedfs` first and fall back to `docker.io/chrislusf/seaweedfs`; the digest is the trust anchor for both. When both pulls fail, provisioning stops with `MANAGED_STORAGE_IMAGE_PULL_FAILED`. The same mirror-first pull applies to the managed database images, the key-value restore staging images, and the default Compose sidecar. SeaweedFS work is dispatched only to nodes that report the `managed_storage_seaweedfs_v1` capability.

Gateway also builds its own SeaweedFS image from `packages/daemons/seaweedfs-image`: the upstream release image with `weed` rebuilt from the same upstream commit plus the patches in `patches/`. Today that is one patch, which keeps S3 downloads of large objects from re-fetching chunks they have not sent yet (upstream issue [#11674](https://github.com/seaweedfs/seaweedfs/issues/11674)). The Image workflow publishes it as `ghcr.io/the-square-labs/gateway/seaweedfs-gateway:tree-<tree hash>` whenever that folder changes, and the docker daemon pins its digest. Build it locally with `scripts/build-seaweedfs-image.sh`. To move to a new upstream release, update the ARGs in the Dockerfile, check that every patch still applies (`git apply --check`), and drop a patch once upstream ships the fix.

A SeaweedFS cluster runs on one server unless it is made available on several (see [Databases And Storage On Several Servers](capabilities.md#databases-and-storage-on-several-servers)), speaks S3 only (no FTP or SFTP), and needs at least 512 MiB of memory. S3 listens on container port 9000; the cluster is private by default and Gateway reaches it over authenticated relay routes. Public S3 publication is a separate setting, and turning it on or off or changing its port recreates the container while keeping data and keys. TLS uses the Gateway Storage CA and is chosen at creation. Every managed storage certificate includes `localhost` and `127.0.0.1`, which backups through the relay require. Gateway renews managed storage certificates automatically and adds those names to older clusters; until the new certificate is served, backups wait in the queue and retry, failing with `BACKUP_STORAGE_CERTIFICATE_OUTDATED` only after 7 hours.

Each access key is its own SeaweedFS IAM principal (`gw-<key id>`) with a bucket-scoped read-only or read-write policy that never grants `s3:ListAllMyBuckets`; scoped keys cannot create or delete buckets. Expiring keys are SeaweedFS service accounts, so the engine enforces the expiry, and revoking a key deletes its principal. Application bindings issue bucket-scoped credentials and provide an endpoint on the application's private binding network. Each TCP connection to that endpoint uses one of the link's 64 concurrent connections, which both slots of a deployment share during a rollout and the node running the workload enforces for the whole link (see [Databases](capabilities.md#databases)); the link's runtime shows its open connections and refusals on the workload's overview and through `get_binding_runtime` of `manage_managed_storage`; S3 SDKs keep large keep-alive pools by default (50 sockets per client in the AWS SDK for JavaScript), so cap the client pool at 32 or less per container. rclone needs `no_check_bucket = true` with a bucket-scoped key.

Each bucket is its own SeaweedFS collection with at least one volume, and volume size and count are derived from the disk size. A full disk returns HTTP 500 for writes while reads keep working; grow the disk, which recreates the container, and writes resume. The engine keeps its Go heap to 60 % of its memory limit and bounds what the volume server holds per transfer, so objects of any size fit the default 768 MiB, and it stores objects in 1 MiB chunks, so large objects are read at full speed (objects uploaded before keep 4 MiB chunks, which SeaweedFS 4.47 reads slowly, at a few MB/s; uploading them again fixes that). A cluster made by an older release gets these settings with its next update or restart, or when the kernel next kills its engine for memory.

### Legacy MinIO clusters

MinIO withdrew its public images, so new MinIO clusters cannot be created. Existing managed MinIO clusters keep running as a legacy engine while the MinIO image is still on the node. Operations that need to pull the image, such as recreating the container after a publication change, a disk grow, or a lost container, fail with `MANAGED_STORAGE_ENGINE_IMAGE_UNAVAILABLE` before the container or its data is touched.

There is no migration button: users ask the built-in assistant (or an MCP client) to migrate a cluster, and it follows the `storage-migration` AI docs topic. The flow creates a SeaweedFS cluster, copies the data online with [storage copy jobs](#storage-copy-jobs), moves or pauses backup policies that write to the cluster, freezes its writes (`freeze_writes`: Gateway-issued keys become read-only and Gateway's own writes, including uploads and backups into the cluster, fail with `STORAGE_WRITES_FROZEN`; refused while a backup or restore using it runs), runs a final `sync` until the report is clean, then imports access keys with their IDs and secrets (`import_access_keys`), moves workload links without recreating the workload (`move_binding`), retargets Route Secure Links (`manage_additional_secure_link retarget`), moves finished backup history (`rehome_backup_history`) and deletes the MinIO cluster. Every step is also available through REST and MCP, and the flow can be rolled back until MinIO is deleted. See the [public migration guide](https://docs.goodgateway.dev/en/storage/overview/#migrating-from-minio).

## Storage copy jobs

A storage copy job copies objects server-side from one S3 connection to another, managed or external, for example from a legacy MinIO cluster to a new SeaweedFS cluster. Copy jobs work only between S3 connections: an SFTP or FTP(S) connection as the source or destination is refused with `400 STORAGE_COPY_PROVIDER_UNSUPPORTED`. Start it with `POST /api/storage/copy-jobs` (`sourceStorageId`, `destinationStorageId`, `buckets`: `"all"` or a list of names, `mode`: `copy` or `sync`, `dryRun`, optional `createBuckets`, `allowLiveDestination`, `executorNodeId` and `limits`) or the `copy_data_start` action of `manage_storage_connection`; follow it with `GET /api/storage/copy-jobs/{id}` (`copy_data_status`), list jobs with `GET /api/storage/copy-jobs` (`copy_data_list`) and stop one with `POST /api/storage/copy-jobs/{id}/cancel` (`copy_data_cancel`).

The backup runner on a Storage node runs a fixed program: `rclone copy` (adds and overwrites, never deletes) or `rclone sync` (also deletes destination objects the source does not have), then `rclone check`. Private managed storage is reached through per-job relay routes, so no port is published and no container is recreated. Objects stream through the executor and are not staged on its disk. Each bucket keeps its name on the destination; missing destination buckets are created only when the job may create them. A dry run writes nothing and reports what differs. A `sync` into managed storage whose writes are not frozen while workload links or writable keys use it is refused with `STORAGE_COPY_DESTINATION_LIVE` unless the request sets `allowLiveDestination: true`. The finished job reports, per bucket and in total, source and destination object counts and bytes, the numbers of missing, differing and (for sync) extra objects with sample keys, and whether everything matched (`clean`). Reruns transfer only what changed, and swapping source and destination copies the other way back.

Starting a job needs `storage:objects:read` and `storage:credentials:use` on the source, `storage:objects:write` and `storage:credentials:use` on the destination, `storage:objects:admin` on the destination to create buckets, and `nodes:backups:execute` on the executor. Credentials are resolved by Gateway for the executor and are never returned to the caller. The executor is chosen among online Storage nodes whose daemon reports `storage_copy_v1` when none is given. Only one active job may write a storage, no job may read a storage another job is writing, and a storage used by an active copy job cannot be deleted. A job that its executor lost (for example after an executor daemon restart) fails and can simply be started again.

## Backup configuration

Gateway releases build and publish the native runner for amd64 and arm64 within the main release workflow, without a separate Git tag or release. Its immutable digest is bundled inside the signed Gateway image. Installation and upgrade use that default automatically, including when an older Compose file passes an empty `BACKUP_RUNNER_IMAGE`. Storage nodes must be able to pull the runner from GHCR. The runner runs only for backup/restore operations; it is not a persistent service.

`BACKUP_RUNNER_IMAGE` is an optional explicit override and must use an immutable `repository@sha256:…` reference. Source/development builds without a bundled runner still require an override. The runner contains the fixed native programs and transport clients; API clients cannot supply commands, scripts, SQL or arbitrary runner images.

In a database's **Backups** tab, select a destination, bucket, prefix and executor Storage node. Policies support manual execution, cron schedules with an explicit time zone, retention count, timeout and workspace/CPU/memory limits. Choose an existing destination bucket. The executor must be able to reach external database and storage endpoints. Private managed resources receive temporary routes for that run; Gateway's own ephemeral loopback ports are not forwarded to the executor.

An executor Storage node runs one backup or restore at a time. Runs admitted while it is busy stay **Queued** (waiting for executor) and start in creation order as soon as the node is free; a queued run can be cancelled immediately. A scheduled policy is skipped for a cron minute while its previous run is still queued or running.

- PostgreSQL uses a native custom-format dump and restores into an empty database.
- Key-value stores capture a native RDB over replication, so the connection's user needs the replication commands (`REPLCONF`, `SYNC`); saving a policy and every run's preflight check this. A backup restores only into the engine it was taken from: a backup of a store that runs Redis restores into a store that runs Redis or into a new store, which then runs the backup's Redis version; a backup of a store that runs Valkey restores only into Valkey. A mismatch fails the restore before the target is touched. Restore loads the verified RDB into an authenticated temporary server of the engine and release line the backup was taken on, performs full replication into an empty target, then detaches it. The target must run that release line or a newer one; a target that cannot load the replicated data fails the run within seconds. Every outcome, a cancel included, returns the target to a stand-alone primary with its original `masterauth` and a saved dataset. External targets require replication/configuration privileges and connectivity back to the executor at its service address, or at an address the node reports when it has none (the same address presigned URLs of its published storage use). Managed targets use their owned private network.
- ClickHouse uses native S3 BACKUP/RESTORE. For a private managed S3 endpoint, choose the managed ClickHouse node as executor; an external ClickHouse server instead needs a server-reachable S3 staging connection. File-protocol destinations require a separate S3 staging connection and bucket reachable directly from the ClickHouse server. Artifacts are transferred between staging and the selected final destination, retaining the native metadata and directory structure.

Restore creates a new managed database by default. Its size and resources (`storageSizeGb`, `cpuCores`, `memoryMb`, `swapMb`, with the limits of managed database create) can be set in the restore request, the restore dialog and MCP; each defaults to the source managed database, and for a backup of an external database to 1 CPU core, 1024 MB of memory (2048 MB for ClickHouse), no swap and three times the backup on disk (at least 20 GB). Native preflight checks target emptiness; the original source is not overwritten. A compatible managed engine version must exist in the curated catalog. Artifact manifests record source identity, server version, sizes and SHA256 checksums. A successful upload alone is not considered a completed backup until its manifest has been validated.

## Permissions and lifecycle

Database permissions distinguish viewing, managing policies, running backups and restoring. `nodes:backups:execute` selects allowed executors. Permission to use a storage's credentials is checked for final and staging destinations: backups, restores, retention and history deletion need only `storage:credentials:use`, which lets the runner (and Gateway, for retention inside the backup's own prefix) use the saved credentials without revealing them to the caller. No `storage:objects:*` scope is needed, so a backup operator does not get the object browser. `storage:credentials:reveal` implies it, and the built-in operator group holds it. Restoring into a new managed database also needs `databases:create` on the Storage node or on the folder chosen for the new database. Scoped tokens retain their own narrower authority. Scheduled runs revalidate the policy actor before execution.

Retention only removes completed artifacts belonging to the run's stored prefix. To remove a backup from history while its files still exist, choose explicitly: **Delete backup and files** removes the files first and keeps the history entry if storage refuses (the error names the reason); **Forget entry** removes only the entry and leaves the files in the bucket, for files that are unreachable or that you keep on purpose. The API takes `artifacts=delete` or `artifacts=forget` on `DELETE /databases/{id}/backups/runs/{runId}`, and the `manage_database_backups` tool takes `config.artifacts`.

Deleting a database keeps its backup history and files. The Databases page lists them under **Backups of deleted databases**, with the name the database had, for callers with the unscoped `databases:backups:view` (deleting a database removes the grants that name it). A completed backup restores from there into a new managed database, which gets the engine and version of the backup, or into another empty connection; removing an entry follows the same file rule as above. The API is `GET /databases/backups/orphaned/runs` with `POST …/{runId}/restore`, `POST …/{runId}/cancel` and `DELETE …/{runId}`, each needing the unscoped `databases:backups:view`, `:restore`, `:run` or `:manage`; the `manage_database_backups` tool has `list_orphaned_runs`, `restore_orphaned`, `cancel_orphaned` and `delete_orphaned_run`.

Storage used by backup policies or by runs that are still active or cleaning up cannot be deleted: delete or re-point those policies and wait for the runs first. Finished backup history, including history of databases that were deleted since, blocks deletion until you confirm forgetting it (`backupHistory=forget` on the storage delete routes, `config.backupHistory` on the storage tools). Forgotten backups can no longer be restored or deleted through Gateway. Their files stay in external storage and are deleted together with a managed storage. A bucket is kept by policies and by history of databases that still exist; history of a deleted database does not keep it, and is removed once the bucket is deleted. Folders that remain after their files were deleted (SeaweedFS keeps them for a while) do not keep a bucket either. The immutable execution request is encrypted while a run is active and removed on terminal completion. Lost command responses retain the node lease; reconnect reconciliation replays the same request or consumes the persisted terminal result. Cancellation remains reconcilable until the daemon confirms a terminal state. Failed or interrupted cleanup retains ownership for a retry.

Existing `databases` nodes retain their identity, enrollment, configuration, and storage root. An ordinary daemon update enables the unified Storage capabilities; re-enrollment, reinstallation, and data relocation are not required. Until updated, an older daemon can only execute workloads supported by its advertised capabilities. No automatic production restart or in-place data migration is part of this feature.
